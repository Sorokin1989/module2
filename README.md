# OrderService — рефакторинг

## Контекст

Исходный `OrderService` содержал метод `processOrder` на ~80 строк, в котором через `if/else if` были зашиты расчёт скидки по типу клиента, расчёт комиссии по способу оплаты, вычисление итоговой суммы, печать чека и сохранение заказа. Любое изменение (новый тип клиента, новый способ оплаты, изменение формата чека) требовало правки этого же метода с риском сломать соседнюю логику.

## Что сделано

Код отрефакторен с применением **SOLID** и паттерна **«Стратегия»**. Поведение сохранено: те же скидки, те же комиссии, та же формула, тот же формат чека.

---

## SOLID

### S — Single Responsibility Principle

**Было нарушено:** один метод `processOrder` делал всё сразу — расчёт скидки, комиссии, итога, печать чека и сохранение заказа. Любое изменение затрагивало один и тот же метод.

**Что исправлено:** ответственности разделены. `model.Order` хранит данные и валидирует их в конструкторе; `DiscountStrategy`/`CommissionStrategy` отвечают за расчёт; `OrderService` — за сценарий обработки; `printer.ReceiptPrinter` — за вывод. Теперь у каждого класса одна причина для изменения.

### O — Open/Closed Principle

**Было нарушено:** скидки и комиссии были реализованы через `if/else if` внутри `OrderService`. Добавление нового типа клиента или способа оплаты требовало изменения этого метода (нарушение OCP).

**Что исправлено:** введён паттерн «Стратегия». Новый тип клиента — это новый класс `XxxDiscount` + константа в `CustomerType`; новый способ оплаты — новый класс `XxxCommission` + константа в `PaymentType`. `OrderService` при этом не меняется: он вызывает `calculateDiscount`/`calculate` через интерфейс.

### L — Liskov Substitution Principle

**Было нарушено:** абстракции для скидок и комиссий не было — всё было зашито в `if/else if`, поэтому нельзя было заменить одну реализацию другой, не меняя метод.

**Что исправлено:** введены интерфейсы `DiscountStrategy` и `CommissionStrategy`. Любая реализация (`RegularDiscount`, `VipDiscount`, `PremiumDiscount`; `CardCommission`, `CashCommission`, `TransferCommission`) взаимозаменяема: `CustomerType` и `PaymentType` работают с интерфейсом, а не с конкретным классом. Все реализации возвращают `BigDecimal` и не нарушают контракт, поэтому подстановка не меняет поведение программы.

### I — Interface Segregation Principle

**Было нарушено:** интерфейсов не было вообще — клиент (метод `processOrder`) зависел от всех веток сразу, и чтобы добавить скидку, нужно было знать про все существующие.

**Что исправлено:** интерфейсы разделены по назначению. `DiscountStrategy` содержит только расчёт скидки, `CommissionStrategy` — только расчёт комиссии. Ни один класс не обязан реализовывать методы, которые ему не нужны: `RegularDiscount` реализует только `calculateDiscount`, `CardCommission` — только `calculate`.

### D — Dependency Inversion Principle

**Было нарушено:** `OrderService` сам создавал зависимости (принтер, список заказов) — жёсткая связь. Заменить принтер (консоль → PDF) или хранилище (память → БД) без правки `OrderService` было нельзя.

**Что исправлено:** зависимости внедряются извне через конструктор: `OrderService(List<Order> orders, ReceiptPrinter receiptPrinter)`. `ReceiptPrinter` не создаётся внутри сервиса — он передаётся из `Main`. Теперь `OrderService` не знает, как создать принтер или список, — он получает их готовыми, и реализацию можно заменить без изменения сервиса.

## Критерий приёмки: поведение сохранено

Формула та же: `finalAmount = amount − discount + commission`.
Скидки: REGULAR = 0%, VIP = 5%, PREMIUM = 10%.
Комиссии: CARD = 2%, CASH = 0%, TRANSFER = 1%.
Формат чека: те же поля (`Order ID`, `Items`, `Base amount`, `Discount`, `Commission`, `Final amount`) и тот же формат чисел (один знак после запятой).
